# AI의 세 칸 칸반 안내 프로토콜

이 문서는 AI가 학생에게 팀 작업 과정을 설명하는 기준입니다. 실행은 각 team 스킬과 [공통 지침](../.agents/skills/team-common.md), [프로젝트 gh 지침](../.agents/skills/team-project.md)을 따릅니다.

## 전체 과정

**작업 준비 → 할 일 보기 → 이슈 선택 → 수정 → PR 제출 → 선생님 병합 → 실제 해결 확인 → 완료 → 반복**

보드는 [프로젝트관리의 칸반](https://github.com/orgs/2026-tmax-it-school/projects/2/views/1)입니다. 칸은 할 일·작업 중·완료이며 수정/PR 검토/병합/QA 대기는 작업 중 안에서 진행합니다. 세부 상황은 이슈와 PR 링크로 설명합니다.

| 역할 | 담당 |
|---|---|
| 동우·영민 | 자기 브랜치에서 한 이슈씩 수정하고 제출 |
| QA | 재현 가능한 이슈 등록·main에서 실제 해결 확인 |
| 선생님 | 필요한 기획 결정·PR 검토·병합 |
| AI | 단계 안내·스킬 실행·충돌 해결·검증 지원 |
| GitHub Action | PR 코드 리뷰 보조 |

## 설명 규칙

- 설명 요청은 설명과 필요한 상태 조회만 허용합니다. 요청 없이 assign·댓글·commit·push·PR 생성·종료를 시작하지 않습니다.
- “어디까지 했지?”에는 실제 계정·브랜치·담당 이슈·프로젝트 Status·PR을 조회합니다. 대화 기억이나 로컬 설정만으로 판단하지 않습니다.
- 이름을 모르면 역할/개인 브랜치만 확인합니다. 로그인명으로 동우·영민을 추측하지 않습니다.
- 단계 실행 전에는 현재 단계와 목적을 한두 문장으로, 실행 후에는 실제 결과·미검증·다음 행동 하나를 안내합니다. 이미 요청한 정상 처리에 반복 승인을 요구하지 않습니다.
- 사용자에게 Git 명령을 외우게 하지 않습니다. 필요한 순간에 브랜치=개인 작업 공간, 커밋=변경 기록, push=업로드, PR=main 반영 요청, 병합=실제 반영이라고 설명합니다.
- 번호·링크·SHA는 조회한 실제 값으로 대체합니다. 아래 예시는 사실로 보고하지 않습니다.
- 수정 완료·push 성공·PR 제출·main 병합·QA 확인은 별개입니다. 실패 단계와 이미 성공한 단계를 구분합니다.

## 단계별 안내

### 1. 작업 준비 — team-sync

학생: “나는 동우야. 작업 준비해줘.”

AI: “동우 브랜치에 최신 팀 작업을 반영하겠습니다. 저장하지 않은 변경부터 확인합니다.”

계정·개인 브랜치를 확인하고 원격 개인 브랜치와 main을 merge합니다. 미커밋 변경은 보호하고 충돌은 해결·검증합니다. main을 직접 수정하거나 push하지 않습니다.

완료 조건: 최신 main 반영, 미해결 충돌 없음, 실제 검증 결과 보고.

결과: “main `<SHA>`를 반영했습니다. 다음에는 ‘할 일 보여줘’라고 말하세요.” 열린 개인 PR이나 확인 대기 이슈가 있으면 그 작업부터 안내합니다.

### 2. 목록 — team-tasks

학생: “할 일 보여줘.”

AI: “보드의 할 일 칸에서 미할당 이슈와 현재 맡은 작업을 확인하겠습니다.”

열린 미할당 이슈 카드의 번호·설명·완료 조건·링크를 표시합니다. ready 라벨은 필요 없습니다. 카드 미등록/상태 불일치/설명 부족은 따로 알려줍니다. 조회만으로 카드·담당자·라벨을 수정하지 않습니다.

완료 조건: 실제 선택 가능한 작업과 내 진행 상황 표시.

결과: “선택할 작업은 #10과 #17입니다. ‘10번 이슈 할게’처럼 번호를 알려주세요.” 일이 없으면 없는 상태를 알리고 다른 사람의 작업을 가져오지 않습니다.

### 3. 선택 — team-claim

학생: “10번 이슈 할게.”

AI: “이슈와 카드의 상태를 다시 확인한 뒤 본인에게 배정하겠습니다.”

열린 이슈·할 일 카드·미할당·현재 진행 작업 없음·완료 조건을 확인합니다. assign 전후 재조회하고 본인 단독 배정이 확인되면 작업 중으로 옮깁니다. 중복 담당이면 시작하지 않습니다.

완료 조건: 본인 배정과 작업 중 카드가 실제 확인됨.

결과: “#10을 배정하고 작업 중으로 옮겼습니다. 다음에는 ‘10번 이슈 수정해줘’라고 말하세요.” 선택 호출 자체는 코드 수정 전체를 시작하지 않습니다.

### 4. 수정 — 일반 개발 요청

학생: “10번 이슈 수정해줘.”

GDD·관련 코드를 읽고 해당 범위에서 수정·검증합니다. 기획 변경은 GDD부터 반영합니다. 수정과 제출을 함께 요청했으면 이어갈 수 있고, 수정만 요청했으면 PR을 자동 제출하지 않습니다.

결과: “수정을 마쳤습니다. `<실제 검증 결과/미검증>`입니다. 제출하려면 ‘작업 제출해줘’라고 말하세요.”

### 5. 제출 — team-submit

학생: “작업 제출해줘.”

AI: “관련 변경을 검증·커밋하고 최신 main을 반영한 뒤 push와 PR 제출을 진행하겠습니다.”

관련 파일만 커밋, 원격 개인 변경/main 반영, 충돌 해결·재검증, 일반 push, main 대상 PR 생성/갱신을 합니다. 미검증은 Draft PR입니다. 본문에 `관련 이슈: #10`, 검증 결과, QA 절차를 쓰고 이슈에도 PR 링크를 남깁니다. 자동 종료 키워드는 사용하지 않습니다.

완료 조건: push와 PR 생성/갱신 확인. 이슈는 열려 있고 카드는 작업 중입니다.

결과: “PR #20을 제출했습니다. 카드는 작업 중이며 선생님의 검토·병합과 QA 확인을 기다립니다.” 열린 PR 동안 같은 개인 브랜치에 다음 작업을 섞지 않습니다.

### 6. 선생님 병합

선생님이 PR과 액션 리뷰를 확인하고 main에 병합합니다. 스킬은 자동 승인·병합하지 않습니다. 개인 브랜치를 계속 사용하므로 기본 병합 방식은 Create a merge commit입니다.

결과: “PR #20이 main에 병합됐습니다. 카드는 아직 작업 중입니다. QA는 ‘10번 이슈 QA 확인해줘’로 실제 결과를 확인하세요.” QA 통과 전에는 개발자에게 다음 선점을 안내하지 않습니다.

### 7. 해결 확인 — team-verify

QA: “10번 이슈 QA 확인해줘.”

AI: “연결 PR의 main 병합과 검증 버전을 확인하고 이슈의 재현 절차를 확인하겠습니다.”

정확한 main SHA에서 재현 절차와 주변 동작을 확인합니다. 필요하면 별도 임시 환경을 사용해 개발자 작업을 보호합니다. 코드 리뷰 액션과 실제 플레이 검증을 구별합니다.

| 결과 | 처리 |
|---|---|
| main 병합 후 해결 확인 | 검증 근거 기록 → 이슈 completed 종료 → 카드 완료 |
| 여전히 재현 | 열린 상태·기존 담당자·작업 중 유지 → 후속 수정 |
| PR 미병합 | 사전 결과만 기록, 종료/완료 금지 |
| 실행 확인 불가 | QA에게 재현 절차 안내, 실제 결과를 받기 전 종료 금지 |

결과: “main `<SHA>`에서 해결을 확인했고 이슈를 닫아 완료로 옮겼습니다. 개발자는 ‘작업 준비해줘’로 다음 작업을 시작하세요.” 이미 닫힌 검증의 반복 요청은 댓글·종료를 중복하지 않습니다. 종료만 성공하고 보드 변경이 실패했다면 차이를 보고하고 카드 상태만 복구합니다.

## 예외 안내

| 상황 | AI 처리 |
|---|---|
| 인증/프로젝트 권한 없음 | 필요한 인증·접근 권한 안내, 라벨로 대체하지 않음 |
| 미커밋 변경 | 보존 후 저장/제출 방법 안내 |
| 중복 선점 | 기존 담당자 보존, 작업 시작 중단 |
| 진행 작업 존재 | 기존 작업을 이어가도록 안내 |
| 코드 충돌 | 양쪽 의도 보존·해결·재검증·결과 보고 |
| 기획 선택 충돌 | 파일·두 의도·필요한 결정만 질문 |
| push 실패 | 원격 반영·재검증 후 제한된 일반 재시도 |
| QA 실패 | 작업 중 유지, 담당자에게 실제 재현 근거 안내 |
| 포기 요청 | 변경 보존·인계·자기 assign 해제·할 일 이동 |
| 보드와 이슈 상태 불일치 | 실제 상태 조회·차이 설명, 요청 범위에서만 복구 |

상태 안내 기본형은 “현재 `<단계>`, 카드 `<상태>`, 이슈 `<번호>`, PR `<상태>`. 다음에는 `<한 가지 행동>`”입니다. 카드 완료로 끌었다는 사실만으로 실제 해결됐다고 설명하지 않습니다.
