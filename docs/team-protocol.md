# AI의 세 칸 칸반 안내 프로토콜

이 문서는 AI가 학생과 관리자에게 팀 작업 과정을 설명하는 기준입니다. 실행은 각 team 스킬과 [공통 지침](../.agents/skills/team-common.md), [프로젝트 gh 지침](../.agents/skills/team-project.md)을 따릅니다.

## 전체 과정

**시작(동기화·목록·선점) → 개발 → 제출 → 관리자 병합 → 다음 개발 반복**

**main 병합 → 이슈 자동 종료·칸반 완료 / QA 학생: 실제 플레이 → 실패 시 기존 이슈 재개**

보드는 [프로젝트관리의 칸반](https://github.com/orgs/2026-tmax-it-school/projects/2/views/1)입니다. 칸은 할 일·작업 중·완료이며 수정/PR 검토/병합 대기는 작업 중, 전체 작업 해결 PR의 main 병합은 완료입니다. QA 확인 여부는 별도로 설명합니다. 세부 상황은 이슈와 PR 링크로 설명합니다.

| 역할 | 담당 |
|---|---|
| 동우·영민·세은 | 자기 브랜치에서 한 이슈씩 수정하고 제출 |
| QA | 재현 가능한 이슈 등록·main에서 실제 해결 확인 |
| 선생님 | 필요한 기획 결정·PR 검토·병합 |
| AI | 단계 안내·스킬 실행·충돌 해결·검증 지원 |
| GitHub Action | PR 코드 리뷰 보조 |

## 역할별 안내 순서

설명은 항상 **학생의 작업 방식**과 **관리자의 작업 방식**을 나눕니다. 학생 안에서는 개발 학생과 QA 학생의 역할을 구분합니다. 각 역할이 언제 무엇을 해야 하는지, 사용할 스킬과 다음 행동을 함께 안내합니다. 현재 질문과 관련된 내용만 간단히 설명합니다.

- 개발 학생: team-start로 시작 → 개발 → team-submit으로 제출 → main 병합 후 다음 작업 시작.
- QA 학생: 제목·내용으로 이슈 작성 → main 병합 후 실제 해결 확인 → 통과 시 결과 댓글, 실패 시 기존 이슈 재개.
- 관리자: 이슈 내용·우선순위 정리 → 진행 상황 확인·조율 → PR 검토·병합 → QA 확인 안내.

이슈 작성 질문에는 담당자·프로젝트·라벨을 직접 지정할 필요가 없고, 버그는 재현 방법·실제 결과·기대 결과를, 기능은 원하는 동작·완료 기준을 적도록 설명합니다. 새 열린 이슈는 자동으로 할 일에 들어갑니다.

칸반 질문에는 학생은 확인용으로 사용하고 정상 흐름의 상태 이동은 자동화와 스킬이 처리한다고 설명합니다. 관리자는 우선순위 조정·상태 오류 복구 시 보드를 수정할 수 있습니다. `Closes #번호`로 연결된 전체 작업 해결 PR은 main 병합 시 자동 종료·완료로 이동합니다. Approve와 병합은 다르며 카드 완료는 QA 통과를 뜻하지 않습니다.

## 설명 규칙

- 설명 요청은 설명과 필요한 상태 조회만 허용합니다. 요청 없이 assign·댓글·commit·push·PR 생성·종료를 시작하지 않습니다.
- “어디까지 했지?”에는 실제 계정·브랜치·담당 이슈·프로젝트 Status·PR을 조회합니다. 대화 기억이나 로컬 설정만으로 판단하지 않습니다.
- 이름을 모르면 역할/개인 브랜치만 확인합니다. 로그인명으로 동우·영민·세은을 추측하지 않습니다.
- 단계 실행 전에는 현재 단계와 목적을 한두 문장으로, 실행 후에는 실제 결과·미검증·다음 행동 하나를 안내합니다. 이미 요청한 정상 처리에 반복 승인을 요구하지 않습니다.
- 사용자에게 Git 명령을 외우게 하지 않습니다. 필요한 순간에 브랜치=개인 작업 공간, 커밋=변경 기록, push=업로드, PR=main 반영 요청, 병합=실제 반영이라고 설명합니다.
- 번호·링크·SHA는 조회한 실제 값으로 대체합니다. 아래 예시는 사실로 보고하지 않습니다.
- 수정 완료·push 성공·PR 제출·main 병합·QA 확인은 별개입니다. 실패 단계와 이미 성공한 단계를 구분합니다.

## 단계별 안내

### 1. 시작 — team-start

개발 학생: “/team-start” (이름을 물으면 본인 이름을 답합니다.)

AI: “동우 브랜치에 최신 main을 반영하고, 맡을 수 있는 이슈를 보여드리겠습니다. 번호를 선택하면 선점까지 진행합니다.”

계정·개인 브랜치·변경·기존 진행 작업을 확인하고 원격 개인 브랜치와 main을 merge합니다. 미커밋 변경은 보호하고 충돌은 해결·검증합니다. 개발 중 이슈·열린 개인 PR이 있으면 기존 작업을 안내합니다. main 병합이 확인된 QA 대기는 따로 보여주고 다음 선점을 허용합니다. 카드 상태나 열린 담당 이슈 수만으로 차단하지 않습니다.

개발 중 작업과 열린 개인 PR이 없으면 보드 할 일 칸의 열린 미할당 이슈를 번호·완료 조건·링크와 함께 보여줍니다. ready 라벨은 필요 없습니다. AI가 임의 선택하지 않습니다.

중간 안내: “main `<SHA>`를 반영했습니다. 선택 가능한 작업은 #10과 #17입니다. 할 이슈 번호를 알려주세요.”

학생: “10번 할게.”

AI는 계정·개인 브랜치·변경·원격과 이슈·카드·담당자를 다시 확인합니다. 필요하면 동기화를 갱신한 뒤 본인 assign 전후를 재조회하고, 단독 배정이 확인되면 작업 중으로 옮깁니다. 중복이면 코드 작업을 시작하지 않습니다.

완료 조건: 최신 main 반영·충돌 해결·검증 결과 보고, 선택한 이슈의 본인 단독 배정과 작업 중 카드 확인.

결과: “#10을 맡아 작업 중으로 옮겼습니다. 다음에는 ‘10번 이슈 수정해줘’라고 말하세요.” 시작 요청만으로 구현 전체를 시작하지 않습니다.

부분 요청도 같은 스킬로 처리합니다. “할 일 보여줘”는 조회만, “동기화해줘”는 동기화만, “10번 이슈 할게”는 필요한 동기화와 선택 이슈 선점을 진행합니다. 목록만 조회할 때 개인 브랜치 설정을 요구하거나 배정·댓글·카드 수정을 하지 않습니다. 이슈가 없으면 없는 상태를 알리고 다른 사람의 작업을 가져오지 않습니다.

### 2. 수정 — 일반 개발 요청

학생: “10번 이슈 수정해줘.”

GDD·관련 코드를 읽고 해당 범위에서 수정·검증합니다. 기획 변경은 GDD부터 반영합니다. 수정과 제출을 함께 요청했으면 이어갈 수 있고, 수정만 요청했으면 PR을 자동 제출하지 않습니다.

결과: “수정을 마쳤습니다. `<실제 검증 결과/미검증>`입니다. 제출하려면 /team-submit을 입력하세요.”

### 3. 제출 — team-submit

학생: “/team-submit”

AI: “관련 변경을 검증·커밋하고 최신 main을 반영한 뒤 push와 PR 제출을 진행하겠습니다.”

관련 파일만 커밋, 원격 개인 변경/main 반영, 충돌 해결·재검증, 일반 push, main 대상 PR 생성/갱신을 합니다. 미검증은 Draft PR입니다. 본문에 `Closes #10`, 검증 결과, QA 절차를 쓰고 자동 종료 연결을 확인하며 이슈에도 PR 링크를 남깁니다. 중간 PR에는 `관련 이슈: #10`만 쓰고 마지막 해결 PR에만 `Closes #10`을 넣습니다.

완료 조건: push와 PR 생성/갱신 확인. 이슈는 열려 있고 카드는 작업 중입니다.

결과: “PR #20을 제출했습니다. 카드는 작업 중이며 선생님의 검토·병합과 QA 확인을 기다립니다.” 열린 PR 동안 같은 개인 브랜치에 다음 작업을 섞지 않습니다.

### 4. 관리자 검토·병합

선생님이 PR과 액션 리뷰를 확인하고 main에 병합합니다. 스킬은 자동 승인·병합하지 않습니다. 개인 브랜치를 계속 사용하므로 기본 병합 방식은 Create a merge commit입니다.

결과: “PR #20이 main에 병합됐습니다. 개발 학생은 /team-start로 다음 작업을 시작하세요. 전체 작업이 해결됐다면 이슈는 자동 종료되고 카드는 완료입니다. QA 학생은 main에서 직접 확인하고 문제를 발견하면 기존 이슈를 다시 여세요.”

### 5. QA 학생의 직접 확인 — 스킬 없음

QA 학생은 연결 PR이 main에 병합됐는지 확인하고 최신 main을 받아 실제 플레이합니다. 이슈 재현 절차와 기대 결과를 확인하고, 통과하면 자동 종료된 이슈에 main 커밋·확인 절차·결과를 댓글로 남깁니다. 종료 조작은 필요 없습니다. 개발 스킬은 QA 확인이나 이슈 종료를 대신 수행하지 않습니다.

실패하면 원래 이슈를 다시 열고 재현 결과를 댓글에 적습니다. 칸반은 작업 중으로 복구하고 자동 반영되지 않으면 관리자에게 요청합니다. 담당 개발자가 새 작업을 진행 중이면 관리자가 수정 순서를 정합니다. 후속 수정은 다른 작업의 PR에 섞지 않습니다. 별도 이슈 생성은 필수가 아닙니다.

main 미병합은 개발 완료로, 실제 실행 미확인은 QA 통과로 안내하지 않습니다. 이슈를 닫았는데 카드가 반영되지 않거나 재개 이슈의 상태가 어긋나면 관리자가 확인·복구합니다. **개발자의 다음 작업 시작과 이슈 자동 완료 기준은 전체 작업 해결 PR의 main 병합이며, QA 통과는 별도 확인**입니다.

## 예외 안내

| 상황 | AI 처리 |
|---|---|
| 인증/프로젝트 권한 없음 | 필요한 인증·접근 권한 안내, 라벨로 대체하지 않음 |
| 미커밋 변경 | 보존 후 저장/제출 방법 안내 |
| 중복 선점 | 기존 담당자 보존, 작업 시작 중단 |
| 개발 중 작업·열린 개인 PR 존재 | 기존 작업을 이어가도록 안내 |
| main 병합 후 QA 대기만 존재 | 기존 이슈·카드 보존, 다음 선점 허용 |
| 코드 충돌 | 양쪽 의도 보존·해결·재검증·결과 보고 |
| 기획 선택 충돌 | 파일·두 의도·필요한 결정만 질문 |
| push 실패 | 원격 반영·재검증 후 제한된 일반 재시도 |
| QA 실패 | QA가 원래 이슈 재개·근거 기록, 작업 중 복구·관리자가 수정 순서 조율 |
| 포기 요청 | 변경 보존·인계·자기 assign 해제·할 일 이동 |
| 보드와 이슈 상태 불일치 | 실제 상태 조회·차이 설명, 요청 범위에서만 복구 |

상태 안내 기본형은 “현재 `<단계>`, 카드 `<상태>`, 이슈 `<번호>`, PR `<상태>`. 다음에는 `<한 가지 행동>`”입니다. 카드 완료로 끌었다는 사실만으로 실제 해결됐다고 설명하지 않습니다.
