# AI와 함께 사용하는 팀 작업 프로토콜

이 문서는 AI가 학생에게 현재 단계와 다음 행동을 설명하는 기준입니다. Git 명령은 AI가 처리하고, 학생은 자기 이름·이슈 번호·작업 요청·필요한 기획 결정을 전달합니다. 실행 세부 규칙은 각 team 스킬과 [공통 지침](../.agents/skills/team-common.md)을 따릅니다.

## 전체 순서

**작업 준비 → 할 일 보기 → 이슈 선택 → 코드 수정 → 작업 제출 → 선생님 병합 → QA 확인 → 반복**

| 역할 | 담당 |
|---|---|
| 동우·영민 | 개인 브랜치에서 이슈 하나씩 수정하고 PR 제출 |
| QA | 재현 가능한 이슈 등록, 병합된 버전 확인, 해결된 이슈 종료 |
| 선생님 | 작업 가능 여부 정리, 필요한 기획 결정, PR 검토·병합 |
| AI | 단계 안내, 계정·작업 상태 확인, 요청한 스킬 실행, 충돌 해결·검증 지원 |

이 문서를 설명해 달라는 요청은 설명과 필요한 상태 조회만 허용합니다. 설명 요청만으로 assign·댓글·커밋·push·PR 생성·이슈 종료를 시작하지 않습니다. 실제 작업은 사용자가 요청한 단계의 범위에서 진행합니다.

## AI가 설명하는 방법

1. 첫 안내에서는 전체 흐름을 한 문단으로 설명합니다. Git 용어는 필요한 순간에 짧게 풉니다. 브랜치는 개인 작업 공간, 커밋은 변경 기록, push는 GitHub 업로드, PR은 main 반영 요청, 병합은 main에 실제 반영하는 것입니다.
2. 사용자가 “어디까지 했지?”라고 하면 실제 계정·브랜치·담당 이슈·PR 상태를 조회합니다. 대화 기억이나 로컬 이슈 설정만으로 단계를 확정하지 않습니다. 이름을 모르면 동우/영민/QA 중 역할을 확인하고 로그인명으로 추측하지 않습니다.
3. 단계 실행 전에는 **현재 단계와 목적**을 한두 문장으로 알립니다. 이미 요청한 단계의 정상 처리에 매번 확인 질문을 추가하지 않습니다.
4. 완료 후에는 **확인된 결과, 미검증/문제, 다음에 할 말 하나**를 알려줍니다. 이슈·PR·커밋이 있으면 실제 번호와 링크/SHA를 넣습니다. 조회하지 않은 번호·결과를 만들지 않습니다.
5. 실패 시 성공한 단계와 실패한 단계를 구분하고, 보호된 변경과 재개 방법을 설명합니다. “완료”라고 뭉뚱그리지 않습니다.
6. 사용자가 선택해야 하는 이슈나 기획 결정을 대신 정하지 않습니다. 필요한 질문은 선택 시점에만 합니다. 작업 목록 조회 후 자동 선점하거나 PR 제출 후 자동 병합하지 않습니다.

아래 대화는 설명 형식의 예시입니다. `#10`, `#20`은 실제 조회 결과로 바꿔야 합니다.

## 1. 작업 준비 — team-sync

**학생:** “나는 동우야. 작업 준비해줘.”

**AI 실행 전:** “동우 브랜치에 팀의 최신 main을 반영하겠습니다. 먼저 저장하지 않은 변경과 진행 중인 작업을 확인합니다.”

계정·저장소·브랜치를 확인하고 개인 브랜치에 원격 개인 변경과 main을 merge합니다. 충돌은 공통 지침에 따라 해결·검증합니다. 개인 브랜치에서 수행하며 main에 직접 push하지 않습니다.

**완료 조건:** 최신 main이 개인 브랜치에 반영됐고, 미해결 충돌이 없으며 필요한 검증 결과를 설명할 수 있습니다.

**AI 결과 예시:** “동우 브랜치에 main의 `<SHA>`를 반영했습니다. 충돌은 없었습니다. 다음에는 ‘할 일 보여줘’라고 말하세요.”

미커밋 변경이 있으면 이를 보존하고 동기화를 멈춥니다. 열린 PR이 있으면 새 이슈를 시작하지 않고 기존 작업을 이어가도록 안내합니다.

## 2. 할 일 보기 — team-tasks

**학생:** “할 일 보여줘.”

**AI 실행 전:** “이슈에서 작업 가능한 미할당 목록과 현재 맡은 작업을 확인하겠습니다.”

ready 라벨이 있고 담당자가 없는 열린 이슈를 번호·문제·완료 조건·링크로 보여줍니다. ready가 없는 이슈는 정리 대기로 구분합니다. 학생이 이미 맡은 수정 작업이나 열린 PR이 있으면 먼저 표시합니다.

**완료 조건:** 실제 작업 가능한 목록과 기존 진행 상황을 보여줬습니다. 조회 자체로 이슈나 코드를 변경하지 않았습니다.

**AI 결과 예시:** “선택 가능한 작업은 #10과 #11입니다. 원하는 번호를 골라 ‘10번 이슈 할게’라고 말하세요.”

선택할 일이 없으면 선생님/QA의 ready 정리가 필요하다고 안내합니다. 다른 사람에게 배정된 작업을 선택 가능 목록에 넣지 않습니다.

## 3. 작업 선택 — team-claim

**학생:** “10번 이슈 할게.”

**AI 실행 전:** “#10이 아직 미할당인지 다시 확인한 뒤 본인 계정에 배정하겠습니다.”

이슈 상태·계정·개인 브랜치·기존 작업을 확인하고 assign 전후 담당자를 다시 조회합니다. 본인 단독 배정이 확인되면 in-progress로 표시하고 시작 내용을 기록합니다. GitHub assign은 완전한 잠금이 아니므로 중복 담당이면 작업을 시작하지 않습니다.

**완료 조건:** 실제 담당자가 본인 하나이고, 작업 범위와 검증 방법을 설명했습니다.

**AI 결과 예시:** “#10을 본인 계정에 배정했습니다. 완료 조건은 열쇠함 설명이 정상적으로 읽히는 것입니다. 다음에는 ‘10번 이슈 수정해줘’라고 말하세요.”

이 단계는 배정까지입니다. 사용자가 이어서 수정 요청을 해야 코드 작업을 시작합니다. 기존 담당이 본인이면 중복 assign·댓글 없이 현재 작업을 안내합니다.

## 4. 코드 수정 — 일반 개발 요청

**학생:** “10번 이슈 수정해줘.”

AI는 GDD와 관련 코드를 읽고 해당 이슈 범위에서 수정합니다. 완료 조건과 재현 방법으로 확인하며, 기획이 바뀌면 GDD를 먼저 갱신합니다. 별도 여섯 번째 팀 스킬은 필요하지 않습니다.

**AI 결과 예시:** “#10 관련 수정을 마쳤습니다. `<실제 검증 결과>`입니다. 제출하려면 ‘작업 제출해줘’라고 말하세요.”

수정 요청만으로 PR 제출까지 요청한 것으로 간주하지 않습니다. 사용자가 수정과 제출을 함께 요청했으면 그 범위에서 이어서 진행할 수 있습니다.

## 5. 작업 제출 — team-submit

**학생:** “작업 제출해줘.”

**AI 실행 전:** “#10 관련 변경을 검증하고 커밋한 뒤 동우 브랜치에 push하겠습니다. 최신 main을 반영한 후 이슈를 연결한 PR을 제출합니다.”

관련 변경만 커밋하고 최신 원격 개인 브랜치·main을 반영합니다. 충돌 해결 후 다시 검증하고 일반 push합니다. main 대상 PR이 이미 있으면 같은 PR을 갱신합니다.

PR에는 `관련 이슈: #10`, 수정 내용, 실제 검증 결과, QA 확인 절차를 적고 이슈에도 PR 링크를 남깁니다. 상태는 in-review로 바꿉니다. 자동 종료 키워드는 사용하지 않습니다.

**완료 조건:** 원격 개인 브랜치에 변경이 올라갔고, 해당 이슈가 연결된 PR을 확인했습니다. 검증 부족이면 Draft입니다. 이슈는 아직 열려 있습니다.

**AI 결과 예시:** “#10 수정 커밋을 push하고 PR #20을 제출했습니다. 이슈는 QA 확인까지 열어둡니다. 이제 선생님의 PR 검토·병합을 기다리세요.”

push 성공 후 PR 생성만 실패했다면 그 사실을 구분합니다. 재개 시 먼저 기존 PR을 조회해 중복 생성을 막습니다. 학생은 PR이 열린 동안 같은 개인 브랜치에서 다음 이슈를 시작하지 않습니다.

## 6. 선생님 검토·병합

선생님이 PR 내용·검증·QA 사전 결과를 확인하고 main에 병합합니다. 계속 사용할 개인 브랜치는 유지하고 기본 병합 방식은 Create a merge commit입니다. AI 리뷰 액션의 의견은 보조 자료입니다.

팀 스킬은 이 단계를 자동 실행하지 않습니다. 학생이 상태를 물으면 PR이 열린 상태/병합됨/미병합으로 닫힘 중 무엇인지 조회해 알려줍니다. 병합됐다는 이유만으로 이슈를 닫지 않습니다.

**AI 안내 예시:** “PR #20이 main에 병합됐습니다. QA는 ‘10번 이슈 QA 확인해줘’로 확인하세요. 개발자는 ‘작업 준비해줘’로 다음 작업을 준비할 수 있습니다.”

## 7. QA 확인 — team-verify

**QA:** “10번 이슈 QA 확인해줘.”

**AI 실행 전:** “연결된 PR의 main 병합 여부와 실제 검증 버전을 확인하고, 이슈의 재현 절차로 결과를 확인하겠습니다.”

병합 후 qa-pending으로 표시하고 해당 변경이 포함된 정확한 main SHA에서 검증합니다. 개발자 작업 폴더를 임의로 바꾸지 않고 필요한 경우 별도 임시 환경을 사용합니다.

| 확인 결과 | 이슈 처리 | AI가 안내할 다음 행동 |
|---|---|---|
| 병합 후 해결 확인 | 검증 근거 기록, 이슈 종료 | 다음 검증할 이슈 선택 |
| 병합 후 여전히 재현 | 열린 상태, ready로 변경, 담당자 유지 | 기존 담당자의 후속 수정 |
| PR 미병합 | 사전 결과만 기록, 종료하지 않음 | 선생님 병합 대기 |
| 실제 플레이 확인 불가 | 미검증, 종료하지 않음 | QA가 실제 결과 제공 |

**AI 통과 예시:** “main `<SHA>`에서 #10의 재현 절차를 확인했고 문제가 해결됐습니다. 검증 결과를 기록하고 이슈를 닫았습니다.”

**AI 실패 예시:** “main `<SHA>`에서도 문제가 재현됩니다. 이슈를 열어두고 결과를 기록했습니다. 기존 담당자가 후속 수정해야 합니다.”

브라우저 도구가 없으면 AI는 QA에게 구체적인 재현 순서와 기대 결과를 안내합니다. QA의 실제 관찰을 받은 뒤 판정하고, 관찰하지 않은 플레이 결과를 만들지 않습니다. 같은 검증 반복 요청은 댓글·종료를 중복하지 않습니다.

## 예외 상황 안내

| 상황 | AI 처리·설명 |
|---|---|
| GitHub 인증/권한 없음 | 필요한 로그인·권한을 안내하고 외부 변경은 수행하지 않음 |
| 미커밋 변경 있음 | 파일을 보존하고 저장/제출 방법부터 안내 |
| 다른 담당자/중복 선점 | 기존 배정을 유지하고 선택 또는 담당 조정 요청 |
| 기존 수정 작업/열린 PR 있음 | 새 선점 대신 현재 작업 진행 안내 |
| 코드 충돌 | 두 의도를 읽고 해결·재검증, 해결 내용을 보고 |
| 기획 선택 충돌 | 파일·양쪽 의도·필요한 결정만 물음 |
| push 거절 | 원격 반영·재검증 후 제한된 일반 재시도, 계속 실패하면 상태 보고 |
| QA 실패 | 이슈 유지, 원래 담당자에게 재현 근거 전달 |
| 작업 포기 | 지정 이슈의 인계·자기 assign 해제, 변경/PR 임의 삭제 금지 |

상태 질문에 대한 기본 응답은 **“현재 `<단계>`, 이슈 `<번호>`, PR `<상태>`. 다음에는 `<한 가지 행동>`”**입니다. 실제 상태가 불명확하면 조회 결과와 확인할 정보를 알려줍니다. 수정 완료, 업로드 완료, PR 제출, main 병합, QA 완료를 서로 구별합니다.
