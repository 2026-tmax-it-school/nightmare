# 학생·관리자 팀 작업 안내

[프로젝트 칸반 열기](https://github.com/orgs/2026-tmax-it-school/projects/2/views/1)

칸은 **할 일 → 작업 중 → 완료** 세 개입니다. 이슈 하나가 카드 하나입니다. PR 카드는 별도로 관리하지 않고 이슈의 PR 링크로 확인합니다.

| 칸 | 의미 |
|---|---|
| 할 일 | 아직 맡지 않은 이슈. ready 라벨 없이 선택 가능 |
| 작업 중 | 개발자가 수정 중이거나 PR 검토·병합·해결 확인 대기 |
| 완료 | main에 병합하고 실제 해결 확인 후 닫은 이슈 |

동우·영민은 개인 브랜치에서 개발하고, QA는 이슈 등록과 실제 플레이 확인, 선생님은 PR 검토·병합을 맡습니다. GitHub Action은 코드 리뷰를 보조합니다.

## 학생의 작업 방식

### 개발 학생 — 동우·영민

| 순서 | AI에게 말할 내용 | 스킬 | 처리 |
|---|---|---|---|
| 1 | 나는 동우야. 작업 준비해줘 | team-sync | 개인 브랜치에 최신 main 반영·충돌 해결 |
| 2 | 할 일 보여줘 | team-tasks | 할 일 칸의 미할당 이슈 조회 |
| 3 | 10번 이슈 할게 | team-claim | 본인 assign 후 작업 중 |
| 4 | 10번 이슈 수정해줘 | 일반 개발 요청 | 해당 범위 수정·검증 |
| 5 | 작업 제출해줘 | team-submit | 커밋·push·main PR, 작업 중 유지 |

한 사람당 진행 작업 하나입니다. 제출 후 관리자 검토·병합과 QA 확인을 기다립니다. QA가 해결을 확인하고 이슈를 닫으면 1번부터 반복합니다. 작업 포기는 “10번 작업 포기하고 인계해줘”로 요청하세요. 변경을 보존하고 자기 assign을 해제한 뒤 할 일로 돌립니다.

### QA 학생 — 이슈 작성과 해결 확인

**새 이슈는 제목과 내용만 작성하면 됩니다.** 프로젝트 선택·담당자 지정·라벨 추가는 필수가 아닙니다. 새로 작성한 열린 이슈는 자동으로 보드의 할 일에 들어갑니다. 담당자는 개발 학생이 team-claim으로 선점할 때 지정합니다.

버그 이슈에는 아래 내용을 적습니다. 사진이나 영상은 있으면 첨부합니다.

```text
제목: [문제가 드러나는 짧은 문장]

재현 방법:
1. 어느 화면이나 장소에서
2. 어떤 조작을 하면

실제 결과: 지금 발생하는 동작
기대 결과: 정상적으로 되어야 하는 동작
```

기능 요청은 원하는 동작과 완료 기준을 적습니다. 한 이슈에는 하나의 문제나 작업을 담습니다.

PR이 main에 병합되면 “10번 이슈 QA 확인해줘”로 team-verify를 사용합니다. 병합된 main에서 실제 플레이 결과를 확인하고, 통과하면 검증 근거를 남겨 이슈를 닫고 완료로 옮깁니다. 실패하면 이슈를 열어 두고 기존 담당자와 작업 중 상태를 유지합니다. GitHub Action의 코드 리뷰만으로 QA를 통과시키지 않습니다.

## 관리자의 작업 방식

1. **작업 정리:** 이슈의 재현 방법·기대 결과 또는 완료 기준이 충분한지 확인합니다. 부족하면 댓글로 보충을 요청하고, 기획 결정이 필요한 부분을 정리합니다.
2. **우선순위 조정:** 중요한 할 일 카드를 위에 배치하고 학생에게 먼저 할 작업을 안내합니다. ready 라벨로 승인하는 단계는 없습니다.
3. **진행 확인:** 칸반에서 담당자와 작업 중 카드를 확인합니다. 세부 진행은 연결된 이슈·PR에서 확인하고 막힌 작업이나 중복 선점을 조율합니다.
4. **PR 검토·병합:** 변경 범위, 검증 결과와 액션 리뷰를 확인합니다. 반영 가능한 PR은 Create a merge commit으로 main에 병합하고 개인 브랜치는 삭제하지 않습니다.
5. **QA 연결:** 병합 후 QA 학생에게 해결 확인을 안내합니다. 실제 확인이 끝날 때까지 작업 중으로 유지합니다.

## 칸반 사용 방식

학생에게 칸반은 주로 **진행 상황 확인용**입니다. 정상 흐름에서는 학생이나 관리자가 카드를 직접 옮길 필요가 없습니다.

| 계기 | 카드 상태를 처리하는 주체 | 결과 |
|---|---|---|
| 새 이슈 작성 | 프로젝트 자동화 | 할 일 |
| 개발 학생이 선점 | team-claim | 작업 중 |
| PR 제출·main 병합 | 작업 중 유지 | 작업 중 |
| QA 통과·이슈 종료 | team-verify와 프로젝트 자동화 | 완료 |

관리자는 우선순위 조정이나 상태 오류 복구가 필요할 때 보드를 수정할 수 있습니다. 상태가 어긋나면 이슈 담당자·PR 병합 여부·QA 근거를 먼저 확인합니다. **카드를 완료로 끌어 놓는 것만으로 해결 확인을 대신하지 않습니다.**

## 처음 한 번

- Git과 GitHub CLI(gh)를 설치하고 본인 계정으로 로그인합니다. `gh auth refresh -s project`로 프로젝트 권한을 인증합니다. 저장소 쓰기 권한과 이 프로젝트 쓰기 권한도 필요합니다. 부족하면 선생님에게 요청하세요.
- 저장소를 최신으로 받고 프로젝트를 다시 열거나 새 대화에서 스킬을 확인합니다. Codex는 `$team-sync`, Claude Code는 `/team-sync`로도 호출할 수 있습니다.
- 학생 이름을 처음 알려주면 개인 브랜치 선택은 해당 PC의 로컬 Git 설정에 저장합니다. 계정명으로 이름을 추측하지 않습니다.

## 운영 규칙

- QA가 이슈에 재현 순서·예상/실제 결과·스크린샷을 적으면 기존 프로젝트 자동화가 열린 이슈를 추가하고 할 일로 배치합니다. 별도 ready 승인은 필요 없습니다. 설명이 부족하면 AI가 필요한 완료 조건을 확인합니다.
- Status와 Assignees만 작업 진행 기준으로 사용합니다. bug/enhancement 같은 분류 라벨은 선택 사항입니다. ready/in-progress/in-review/qa-pending 상태 라벨은 쓰지 않습니다.
- 담당자가 있는 할 일 카드는 다른 사람이 가져오지 않습니다. AI가 상태 불일치를 안내하면 원래 담당자와 선생님이 확인합니다.
- 선생님은 개인 브랜치를 계속 쓰는 동안 Create a merge commit으로 병합하고 브랜치를 삭제하지 않습니다.
- PR 본문은 `관련 이슈: #10`으로 연결하고 이슈에도 PR 링크를 남깁니다. 자동 종료 키워드는 쓰지 않습니다.
- PR 병합 뒤에도 작업 중입니다. QA가 실제 해결을 확인한 뒤 이슈를 닫고 완료로 이동합니다. 실패하면 담당자와 작업 중 상태를 유지합니다.
- 카드만 완료로 끌어도 이슈가 자동 종료되지는 않습니다. 종료는 QA 스킬에서 검증 후 처리합니다.

## 충돌과 검증

동기화·제출 스킬이 두 변경의 의도를 읽고 코드 충돌을 해결·재검증합니다. 기획 선택이 필요한 경우만 결정 내용을 묻습니다. 미커밋 변경은 보호하며 force push나 변경 삭제로 해결하지 않습니다.

GitHub assign은 완전한 잠금이 아니므로 선점 전후 담당자를 재확인합니다. 중복이면 작업을 시작하지 않습니다.

게임은 `python3 tools/serve.py`, 개발자 모드는 `/?dev`입니다. UI 변경은 실제 플레이로 확인합니다. 실행 미검증 제출은 Draft PR로 남깁니다. AI 리뷰 성공만으로 QA 통과를 주장하지 않습니다.

AI의 안내 방식과 예외 처리는 [팀 작업 프로토콜](team-protocol.md), 실행 공통 규칙은 [공통 지침](../.agents/skills/team-common.md)을 참고하세요. 보드 연결 정보는 `.agents/team-project.json`에서 관리합니다.
