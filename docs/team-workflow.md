# 학생 팀 작업 순서

동우·영민은 자기 이름의 브랜치에서 작업하고 QA는 이슈 등록·수정 확인, 선생님은 main 병합을 맡습니다.

| 순서 | 말할 내용 | 스킬 | 결과 |
|---|---|---|---|
| 1 | 작업 준비해줘 | team-sync | 최신 main 반영·충돌 해결 |
| 2 | 할 일 보여줘 | team-tasks | ready 미할당 이슈·내 진행 상황 |
| 3 | 10번 이슈 할게 | team-claim | 자기 배정·완료 조건 안내 |
| 4 | 수정 요청 후, 작업 제출해줘 | team-submit | 검증·커밋·push·main PR |
| 5 | 10번 이슈 QA 확인해줘 | team-verify | 병합된 main 검증·이슈 종료 |

선택 스킬은 배정까지 합니다. 이어 원하는 코드 수정을 요청하세요. PR이 열린 동안 같은 개인 브랜치에서 다음 이슈를 시작하지 않습니다. 병합 후에는 1번부터 반복하고 QA는 main의 결과를 확인합니다.

## 이슈와 PR

QA는 재현 순서·예상/실제 결과·체크포인트·스크린샷을 적습니다. 선생님 또는 QA가 작업 가능 이슈에 ready를 붙입니다. ready가 없으면 목록에서 정리 대기로 표시합니다.

상태는 `ready → in-progress → in-review → qa-pending → 종료`입니다. qa-pending은 병합 후 QA 스킬 호출 시 표시하며 자동 액션은 아닙니다. QA 실패는 ready로 돌아가고 담당자는 유지합니다. 포기할 때는 “10번 작업 포기하고 인계해줘”라고 명시하세요.

PR은 `관련 이슈: #10`으로 연결하고 이슈에도 PR 링크를 남깁니다. 자동 종료 키워드는 쓰지 않습니다. **선생님이 main에 병합하고 QA가 그 버전을 실제 확인한 뒤 이슈를 닫습니다.** 개인 브랜치를 계속 쓰는 동안 Create a merge commit으로 병합하고 브랜치를 삭제하지 마세요. squash/rebase 병합은 다음 작업 전에 개인 브랜치 이력을 정리해야 할 수 있습니다.

## 충돌과 검증

동기화·제출 스킬이 양쪽 의도를 읽고 코드 충돌을 해결합니다. 기획 중 하나를 골라야 하면 필요한 결정만 물어봅니다. 변경 삭제·force push로 해결하지 않습니다. 미커밋 변경은 보관 방법부터 안내합니다.

GitHub assign은 완전한 잠금이 아닙니다. 선점 전후 확인해 중복이면 멈춥니다. 같은 파일을 동시에 수정할 일이 보이면 선생님이 작업을 나눠주세요.

게임은 `python3 tools/serve.py`, 개발자 모드는 `/?dev`입니다. UI 변경은 실제 플레이로 확인합니다. 실행 미검증 제출은 Draft PR로 남깁니다. AI 액션은 코드 리뷰 보조이며 충돌 해결·게임 검증·병합을 대신하지 않습니다.
