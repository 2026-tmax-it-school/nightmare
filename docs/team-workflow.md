# 학생·관리자 팀 작업 안내

[프로젝트 칸반 열기](https://github.com/orgs/2026-tmax-it-school/projects/2/views/1)

칸은 **할 일 → 작업 중 → 완료** 세 개입니다. 이슈 하나가 카드 하나입니다. PR 카드는 별도로 관리하지 않고 이슈의 PR 링크로 확인합니다.

| 칸 | 의미 |
|---|---|
| 할 일 | 아직 맡지 않은 이슈. ready 라벨 없이 선택 가능 |
| 작업 중 | 개발자가 수정 중이거나 PR 검토·병합 대기 |
| 완료 | 전체 작업을 해결하는 PR이 main에 병합되어 자동 종료된 이슈. QA 확인 여부는 별도 |

스킬은 **team-start(시작)·team-submit(제출)** 두 개입니다.

동우·영민은 개인 브랜치에서 개발하고, QA는 이슈 등록과 실제 플레이 확인, 선생님은 PR 검토·병합을 맡습니다. GitHub Action은 코드 리뷰를 보조합니다.

## 학생의 작업 방식

### 개발 학생 — 동우·영민

| 순서 | AI에게 말할 내용 | 스킬 | 처리 |
|---|---|---|---|
| 1 | /team-start | team-start | 동기화 → 목록 → 학생이 번호 선택 → 선점 |
| 2 | 10번 이슈 수정해줘 | 일반 개발 요청 | 해당 범위 수정·검증 |
| 3 | /team-submit | team-submit | 커밋·push·main PR, 작업 중 유지 |

이름을 물어보면 본인 이름(동우/영민)을 입력하세요. 시작 스킬이 목록을 보여주면 “10번 할게”처럼 번호만 답하면 됩니다. AI가 임의로 선택하지 않습니다. 목록만 보고 싶으면 “할 일 보여줘”, 동기화만 필요하면 “동기화해줘”라고 요청할 수 있습니다. 모두 team-start가 요청한 범위만 처리합니다.

한 사람당 개발 중 작업 하나, 열린 PR 하나입니다. 제출 후 관리자 검토·병합을 기다립니다. **전체 작업을 해결한 PR이 main에 병합되면 QA 확인을 기다리지 않고 1번부터 다음 작업을 시작합니다.** 중간 PR만 병합했다면 같은 이슈의 남은 작업을 이어갑니다. 전체 작업이 해결되면 이슈는 자동 종료되고 칸반은 완료가 됩니다. QA는 병합 결과를 별도로 확인합니다. 작업 포기는 “10번 작업 포기하고 인계해줘”로 요청하세요. 변경을 보존하고 자기 assign을 해제한 뒤 할 일로 돌립니다.

### QA 학생 — 이슈 작성과 해결 확인

**새 이슈는 제목과 내용만 작성하면 됩니다.** 프로젝트 선택·담당자 지정·라벨 추가는 필수가 아닙니다. 새로 작성한 열린 이슈는 자동으로 보드의 할 일에 들어갑니다. 담당자는 개발 학생이 team-start로 선점할 때 지정합니다.

버그 이슈에는 아래 내용을 적습니다. 사진이나 영상은 있으면 첨부합니다.

```text
제목: [문제가 드러나는 짧은 문장]

재현 방법:
1. 어느 화면이나 장소에서
2. 어떤 조작을 하면

실제 결과: 지금 발생하는 동작
기대 결과: 정상적으로 되어야 하는 동작
```

기능 요청은 원하는 동작과 완료 기준을 적습니다. 관련된 작은 문제는 하나의 작업으로 묶을 수 있습니다. 해결 범위와 완료 기준을 명확히 적습니다.

QA용 스킬은 없습니다. QA 학생이 다음 순서로 직접 진행합니다.

1. 연결 PR이 main에 병합됐는지 확인하고, 최신 main을 받아 실행합니다. 개발 학생의 미병합 브랜치와 혼동하지 않습니다.
2. 이슈의 재현 방법과 기대 결과대로 실제 플레이합니다.
3. 통과하면 자동 종료된 이슈에 확인한 main 커밋·재현 절차·결과를 댓글로 남깁니다. 추가 종료 조작은 필요 없습니다.
4. 실패하면 원래 이슈를 **Reopen issue**로 다시 열고 재현 방법·실제 결과를 댓글에 남깁니다. 칸반을 작업 중으로 복구하며 자동 반영되지 않으면 관리자에게 요청합니다. 담당 개발자가 새 작업 중이면 관리자에게 수정 순서 조율을 요청합니다. 별도 이슈를 만들 필요는 없습니다.

개발 학생은 병합 이후 다음 작업을 진행할 수 있습니다. GitHub Action의 코드 리뷰만으로 실제 플레이 확인을 대신하지 않습니다.

## 관리자의 작업 방식

1. **작업 정리:** 이슈의 재현 방법·기대 결과 또는 완료 기준이 충분한지 확인합니다. 부족하면 댓글로 보충을 요청하고, 기획 결정이 필요한 부분을 정리합니다.
2. **우선순위 조정:** 중요한 할 일 카드를 위에 배치하고 학생에게 먼저 할 작업을 안내합니다. ready 라벨로 승인하는 단계는 없습니다.
3. **진행 확인:** 칸반에서 담당자와 작업 중 카드를 확인합니다. 세부 진행은 연결된 이슈·PR에서 확인하고 막힌 작업이나 중복 선점을 조율합니다.
4. **PR 검토·병합:** 변경 범위, 검증 결과와 액션 리뷰를 확인합니다. 반영 가능한 PR은 Create a merge commit으로 main에 병합하고 개인 브랜치는 삭제하지 않습니다.
5. **QA 연결:** 병합 후 QA 학생에게 해결 확인을 안내합니다. 전체 작업 해결 PR의 병합으로 이슈는 자동 종료되고 카드가 완료로 이동합니다. QA 미확인은 별도로 안내하고, 개발 학생은 다음 작업을 시작하도록 안내합니다. QA 실패 시 후속 수정 순서를 조율합니다.

## 칸반 사용 방식

학생에게 칸반은 주로 **진행 상황 확인용**입니다. 정상 흐름에서는 학생이나 관리자가 카드를 직접 옮길 필요가 없습니다.

| 계기 | 카드 상태를 처리하는 주체 | 결과 |
|---|---|---|
| 새 이슈 작성 | 프로젝트 자동화 | 할 일 |
| 개발 학생이 선점 | team-start | 작업 중 |
| PR 제출·승인, 중간 PR 병합 | 작업 중 유지 | 작업 중 |
| 전체 작업 해결 PR의 main 병합 | `Closes #번호` → 이슈 자동 종료 → 프로젝트 자동화 | 완료 |
| QA 실패·이슈 재개 | QA 학생이 재개, 자동화 미반영 시 관리자 복구 | 작업 중 |

관리자는 우선순위 조정이나 상태 오류 복구가 필요할 때 보드를 수정할 수 있습니다. 상태가 어긋나면 이슈 담당자·PR 병합 여부·QA 근거를 먼저 확인합니다. **카드를 완료로 끌어 놓는 것만으로 해결 확인을 대신하지 않습니다.**

## 처음 한 번

- Git과 GitHub CLI(gh)를 설치하고 본인 계정으로 로그인합니다. `gh auth refresh -s project`로 프로젝트 권한을 인증합니다. 저장소 쓰기 권한과 이 프로젝트 쓰기 권한도 필요합니다. 부족하면 선생님에게 요청하세요.
- 저장소를 최신으로 받고 프로젝트를 다시 열거나 새 대화에서 스킬을 확인합니다. Codex는 `$team-start`, Claude Code는 `/team-start`로도 호출할 수 있습니다.
- 학생 이름을 처음 알려주면 개인 브랜치 선택은 해당 PC의 로컬 Git 설정에 저장합니다. 계정명으로 이름을 추측하지 않습니다.

## 운영 규칙

- QA가 이슈에 재현 순서·예상/실제 결과·스크린샷을 적으면 기존 프로젝트 자동화가 열린 이슈를 추가하고 할 일로 배치합니다. 별도 ready 승인은 필요 없습니다. 설명이 부족하면 AI가 필요한 완료 조건을 확인합니다.
- Status와 Assignees만 작업 진행 기준으로 사용합니다. bug/enhancement 같은 분류 라벨은 선택 사항입니다. ready/in-progress/in-review/qa-pending 상태 라벨은 쓰지 않습니다.
- 담당자가 있는 할 일 카드는 다른 사람이 가져오지 않습니다. AI가 상태 불일치를 안내하면 원래 담당자와 선생님이 확인합니다.
- 선생님은 개인 브랜치를 계속 쓰는 동안 Create a merge commit으로 병합하고 브랜치를 삭제하지 않습니다.
- PR 본문에 `Closes #10`을 넣고 이슈에도 PR 링크를 남깁니다. 이슈 하나를 여러 PR로 나누면 중간 PR은 `관련 이슈: #10`만 쓰고, 전체 완료 기준을 충족하는 마지막 PR에만 `Closes #10`을 넣습니다.
- Approve만으로는 종료되지 않습니다. 전체 작업 해결 PR을 main에 병합하면 이슈가 자동 종료되어 완료로 이동합니다. QA 실패 시 기존 이슈를 다시 열고 담당자를 유지하며 작업 중으로 복구합니다.
- 카드만 완료로 끌어도 이슈가 자동 종료되지는 않습니다. 종료는 PR의 main 병합과 자동 종료 연결로 처리합니다.

## 충돌과 검증

시작·제출 스킬이 두 변경의 의도를 읽고 코드 충돌을 해결·재검증합니다. 기획 선택이 필요한 경우만 결정 내용을 묻습니다. 미커밋 변경은 보호하며 force push나 변경 삭제로 해결하지 않습니다.

GitHub assign은 완전한 잠금이 아니므로 선점 전후 담당자를 재확인합니다. 중복이면 작업을 시작하지 않습니다.

게임은 `python3 tools/serve.py`, 개발자 모드는 `/?dev`입니다. UI 변경은 실제 플레이로 확인합니다. 실행 미검증 제출은 Draft PR로 남깁니다. AI 리뷰 성공만으로 QA 통과를 주장하지 않습니다.

AI의 안내 방식과 예외 처리는 [팀 작업 프로토콜](team-protocol.md), 실행 공통 규칙은 [공통 지침](../.agents/skills/team-common.md)을 참고하세요. 보드 연결 정보는 `.agents/team-project.json`에서 관리합니다.
