# 작업 제출

먼저 저장소 루트의 `.agents/skills/team-common.md`를 읽는다.

1. 계정·개인 브랜치·선택한 열린 이슈·본인 단독 배정을 확인한다. base=main, head=내 브랜치인 열린 PR을 찾는다. 다른 이슈의 열린 PR이 있으면 섞지 않고 멈춘다. 번호가 불명확하면 확인한다.
2. staged/unstaged diff·기존 미푸시 커밋·merge-base 기준 PR diff를 읽는다. 무관한 staged 파일도 제외하고 관련 파일/부분만 명시적으로 stage한다. 사용자 변경을 보존한다. 이슈 밖의 커밋이 섞이면 제출을 멈추고 분리 방법을 안내한다.
3. GDD·완료 조건에 따라 기능 검증한다. 실패는 해당 범위에서 수정한다. 플레이 검증 불가능이면 미검증 이유를 적은 Draft PR로 제출해 QA 확인을 요청한다. 검증 성공을 꾸미지 않는다.
4. 관련 변경을 `fix: ... (#번호)` 등으로 커밋한다. 이미 커밋됐으면 빈 커밋을 만들지 않는다. 무관한 미커밋 변경이 남으면 동기화 전에 저장 방법을 사용자와 정한다.
5. 공통 동기화·충돌 절차로 원격 개인 브랜치와 최신 main을 반영하고 재검증한다. unresolved·diff --check·merge-base 기준 최종 diff를 확인한다. 변경이 없으면 PR을 만들지 않고 상황을 설명한다.
6. 일반 `git push -u origin <내 브랜치>` 후 성공을 확인한다. 실패는 공통 제한 재시도를 따른다. 기존 PR이면 갱신하고 없으면 main 대상 PR을 만든다. 같은 head의 PR을 중복 생성하지 않는다.
7. PR 본문은 UTF-8 파일과 --body-file로 전달한다. `관련 이슈: #번호`와 이슈 URL, 문제/수정 후 동작, 실제 검증·미검증, QA 재현 순서/체크포인트·기대 결과, 충돌 해결 요약, “QA가 main 병합 결과를 확인한 뒤 이슈를 닫습니다.”를 포함한다.
8. Closes/Fixes/Resolves 등 자동 종료 키워드는 쓰지 않는다. 기존 PR의 해당 이슈 자동 종료 문구도 제거하되 무관한 본문은 보존한다. 번호·URL로 참조 연결하고 지원 도구가 있으면 Development 연결도 추가한다. 이슈에 PR 링크를 한 번 남기고 기존 동일 링크 댓글은 반복하지 않는다.
9. 새 PR 생성 후 환경에 PR 첨부 도구가 있으면 반드시 첨부한다. 결과가 불명확하면 PR/댓글을 조회해 복구한다. 이슈 상태를 in-review로 바꾼다. Draft의 ready 전환은 실제 검증 후에만 한다. 기존 액션 외 별도 유료 리뷰를 호출하지 않는다.
10. PR 링크·커밋·실제 검증·병합/QA 대기 상태를 보고한다. 열린 PR이 있는 동안 같은 개인 브랜치에서 다음 이슈를 시작하지 않도록 안내한다. PR을 자동 병합하거나 이슈를 닫지 않는다.
