# 작업 시작

먼저 저장소 루트의 `.agents/skills/team-common.md`와 그 문서가 연결하는 안내·프로젝트 지침을 읽는다.

## 요청 범위

- “작업 시작해줘”는 개인 브랜치 동기화 → 할 일 목록 → 학생의 선택 → 선점까지 진행한다. 선택 번호가 없으면 목록을 보여주고 응답을 기다린다. AI가 임의 선택하거나 첫 요청만으로 배정하지 않는다.
- “할 일 보여줘”는 읽기 전용 목록만, “동기화해줘”는 동기화만 수행한다. 목록만 볼 때 개인 브랜치 설정을 요구하지 않는다.
- “10번 이슈 할게”처럼 번호를 선택하면 최신 상태를 재확인하고 필요한 동기화 후 선점한다. 설명만 요청하면 배정·댓글을 하지 않는다.
- 특정 이슈 포기 요청은 공통 인계 절차로 변경을 보존하고 자기 assign·상태·무효한 로컬 이슈 설정을 해제한다.

## 시작과 동기화

1. 계정·origin·개인 브랜치·현재 변경·내 담당 이슈·열린 개인 PR을 확인한다. 공통 지침으로 개발 중 작업과 main 병합 후 QA 대기를 구분한다. 개발 중 작업이나 열린 개인 PR이 있으면 새 선점 대신 기존 작업의 단계와 다음 행동을 안내한다. 요청 범위에서 동기화는 가능하다.
2. 공통 안전한 동기화·충돌 해결 절차로 원격 개인 브랜치와 origin/main을 개인 브랜치에 반영하고 검증한다. 미커밋 변경이나 기존 merge/rebase는 보호하고 문제가 해결되기 전 선점하지 않는다. 이 스킬은 push하지 않는다.
3. 이전 PR 병합 뒤 merge-base와 diff로 중복 변경을 확인한다. squash/rebase 병합 등으로 중복이 남으면 선생님에게 브랜치 정리를 요청하고 임의 reset하지 않는다.

## 목록과 학생의 선택

4. 프로젝트 이슈 카드와 열린 이슈의 번호·제목·body·assignees·labels·URL을 대조한다. 모든 페이지를 조회하거나 제한/누락을 표시한다. 작업 목록에서 닫힌 이슈와 PR은 제외한다. 기존 로컬 이슈가 닫혔으면 연결 PR과 종료 근거를 확인해 이전 작업으로 구분한다.
5. 내 개발 중 작업·QA 대기·후속 수정 대기를 나눠 요약한다. 개발 중 작업과 열린 개인 PR이 없으면 할 일 칸의 열린 미할당 이슈를 번호·완료/재현 조건·실제 우선순위·링크와 함께 보여준다. 우선순위·난이도를 추측하지 않고 ready 라벨을 요구하지 않는다. 미등록/상태 불일치/설명 부족은 별도로 알리고 조회만으로 수정하지 않는다.
6. 번호를 받지 않았다면 “어떤 이슈를 할지 번호를 알려주세요”라고 안내하고 기다린다. 대화가 이어지면 계정·브랜치·변경·진행 작업과 선택 이슈를 재조회한다. 이전 목록만 믿고 배정하지 않는다. 원격이 바뀌었다면 동기화·검증을 갱신한다.

## 선점과 시작 완료

7. 새 선점은 선택 이슈의 열린 상태·할 일 카드·미할당·재현/완료 조건·내 다른 개발 중 작업 없음·열린 개인 PR 없음을 확인한다. 조건이 부족하면 필요한 내용만 묻는다. 본인 단독 배정 이슈는 실제 PR 상태로 기존 작업·QA 대기를 구분하고 배정·댓글을 반복하지 않는다. 병합 완료로 닫힌 이슈를 선택한 경우 새 선점하지 않고, 후속 수정이라면 먼저 QA 실패로 재개됐는지 확인한다. QA 실패로 후속 수정을 선택했다면 공통 지침에 따라 순서를 확인하고 로컬 이슈 번호를 갱신해 기존 이슈를 이어간다.
8. 배정 직전 담당자를 재조회하고 유효하면 `gh issue edit <번호> --repo 2026-tmax-it-school/nightmare --add-assignee @me`를 실행한다. 즉시 다시 조회해 본인 단독 배정을 확인한다. assign은 원자적 잠금이 아니다. 여러 담당자가 생기면 코드 작업·상태 변경을 멈추고 중복 선점을 알린다. 다른 담당자를 제거하지 않는다.
9. 단독 배정 확인 후 프로젝트 카드를 작업 중으로 바꾸고 확인한 번호를 로컬 nightmare.team-issue에 저장한다. 상태 변경 실패와 배정 성공은 구분해서 보고한다. 보드 변경을 확인하기 전 시작 완료로 안내하지 않는다.
10. 브랜치·작업 범위의 시작 댓글을 한 번 남긴다. 같은 계정의 기존 시작 댓글은 반복하지 않는다. GDD·관련 코드를 읽고 완료 조건과 검증 방법을 안내한다. 이 호출만으로 기능 구현 전체를 시작하지 않는다.

결과에는 브랜치·반영 main SHA·이슈·실제 카드 상태·충돌/검증 결과와 다음 행동 하나를 안내한다. 예: “#10을 맡아 작업 중으로 옮겼습니다. 이제 ‘10번 이슈 수정해줘’라고 말하세요.” 동기화만 또는 목록만 요청한 경우에는 실제 수행 범위만 보고한다.
